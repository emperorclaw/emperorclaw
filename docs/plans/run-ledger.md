# Run ledger, delivery inspector and data retention

Status: planned · Owner: Jose · Created: 2026-10-13

## Why

Every runtime incident in October 2026 (stale Pi bridges dropping peer messages, ghost runtimes answering as another agent, escalations silently `loop_paused`, a bridge self-registering a duplicate agent) took hours of SQL and nginx log reading to diagnose, because a turn leaves no record. At the same time the database already leaks: `idempotency_keys` holds ~330,000 rows back to March (292k from `/tasks/claim` alone) and is ~69% of the production database, because nothing ever deletes them.

This plan adds a per-turn **run ledger** and a **delivery inspector**, and puts **data retention** in place first so neither the new tables nor the existing ones grow without bound.

## Goals

1. Answer "why didn't agent X reply to message Y?" in one click.
2. See each agent's recent turns: trigger, duration, outcome, tokens, cost, errors.
3. Detect runtimes that die mid-turn (runs that never finish).
4. Bounded storage: every high-volume table has a TTL, a batched cleanup job, and visible size.

Non-goals (later): per-tool traces, cron/objective-triggered runs, Postgres partitioning (only when a table passes ~20M rows), runtime identity lease and bridge self-update (separate plans).

## Facts this design builds on

- Periodic jobs run in `runLifecycleMonitor` (`src/lib/lifecycle.ts`), started from `src/instrumentation.ts`, 15 s tick under `pg_try_advisory_lock(20261011)`; sub-jobs gate on `last*Check` timestamps. The stall sweep uses xact lock `1937006962`, objectives `1937006963`. **Retention takes `1937006964`.**
- Bridges already report: `/agents/report-usage` (tokens only, no message link → `token_usage_log`), `/agents/heartbeat`, `/chat/status` (typing, activity, `executionState` → `thread_messages.delivery_state`), `/chat/reasoning`. There is no per-turn record; `agent_sessions` is per session.
- `decideDelivery` (`src/lib/message-routing.ts`) is pure, but a past verdict cannot be reproduced faithfully (live roster, env caps, sync-batch-anchored 200-message tail, `filterAnsweredMessages`). **So the verdict is stored, not recomputed.**
- Platform admin console: `src/app/(app)/ops/` (`requirePlatformAdminSession`). No table-size reporting exists.
- Latest migration: `0057_live-feed-agent-thoughts`. Next: `0058_…` via `drizzle-kit generate --name`.

## Data model (migration 0058)

### `agent_runs` — one row per turn (detail, 30-day TTL)
| column | type | notes |
|---|---|---|
| id | uuid pk | **generated by the runtime** so start/finish are idempotent and retry-safe |
| company_id | uuid fk cascade | |
| agent_id | uuid fk set null | |
| runtime_id | text | bridge `RUNTIME_ID` (e.g. `hermes-qa-malecu-hermes-1`) — also exposes duplicate runtimes |
| runtime_kind | text | `hermes` \| `codex` \| `openclaw` \| other |
| bridge_version | text | reported by the bridge |
| trigger_kind | text | `message` \| `task` \| `objective` \| `other` |
| trigger_message_id | uuid null | the message that started the turn |
| thread_id | uuid null | |
| task_id | uuid null | |
| reply_message_id | uuid null | set on finish |
| status | text | `running` \| `succeeded` \| `failed` \| `timeout` \| `cancelled` \| `blocked` \| `lost` |
| started_at / ended_at | timestamp | |
| duration_ms | integer null | |
| input_tokens / output_tokens | integer null | |
| cost_cents | integer null | |
| tool_calls | integer null | count only, no traces |
| error | text null | truncated to 500 chars, redacted with the live-feed redactor |

Indexes: `(company_id, agent_id, started_at desc)`, `(trigger_message_id)`, partial `(status) where status = 'running'`. Row size target ≤ ~400 bytes. No message text, no reasoning.

### `message_routes` — delivery verdicts that matter (14-day TTL)
One row per (message, agent) **only when interesting**: `addressedToYou = true`, or the agent was mentioned/targeted/paired but not addressed (`loop_paused`, `targeted_other`, a mention that lost to an ambiguity). `self` and plain `not_addressed` are never stored.

| column | notes |
|---|---|
| company_id, message_id, agent_id | unique `(message_id, agent_id)`; upsert keeps the latest verdict |
| addressed | boolean |
| route_reason | the `RouteDecision.routeReason` |
| agent_streak / max_turns | the loop-guard inputs at decision time |
| decided_at | timestamp |

Written by the sync route at the moment it routes (batched insert, `onConflictDoUpdate`).

### `agent_run_daily` — rollups (kept 400 days)
`(company_id, agent_id, day)` unique; `runs, succeeded, failed, timeout, lost, p50_ms, p95_ms, input_tokens, output_tokens, cost_cents, tool_calls`. ~1 row per agent per day.

### `idempotency_keys`
Add index on `created_at`. TTL 48 h (a key only needs to outlive a client's retry window).

## Retention job (`src/lib/retention.ts`)

Runs hourly from `runLifecycleMonitor` under xact lock `1937006964`, each step bounded so a tick never holds locks for long:

1. **Close lost runs:** `running` rows older than `max(runtime timeout, 2 h)` → `lost`, `ended_at = now`.
2. **Roll up** finished days not yet in `agent_run_daily` (idempotent upsert).
3. **Delete in batches** (`DELETE … WHERE id IN (SELECT id … LIMIT 5000)`), looping up to a per-tick budget (e.g. 50k rows or 20 s):
   - `agent_runs` older than `EMPEROR_RUN_RETENTION_DAYS` (default 30), only after their day is rolled up
   - `message_routes` older than `EMPEROR_ROUTE_RETENTION_DAYS` (default 14)
   - `idempotency_keys` older than `EMPEROR_IDEMPOTENCY_TTL_HOURS` (default 48)
   - `agent_run_daily` older than 400 days
4. Record a `retention_runs` summary (rows deleted per table, duration) in the existing ops/error log or a small table, for the Ops page.

First deploy: the idempotency backlog (~330k rows) drains over a few ticks thanks to the per-tick budget — no long lock, no manual step. Run `VACUUM (ANALYZE)` is left to autovacuum; document a one-off `VACUUM FULL idempotency_keys` as optional to return disk to the OS.

Scaling path (documented, not built): when `agent_runs` passes ~20M rows, switch to monthly declarative partitions and drop old partitions instead of deleting.

## API

- `POST /api/mcp/agents/runs` `{ id, agentId, runtimeId, runtimeKind, bridgeVersion, triggerKind, triggerMessageId?, threadId?, taskId?, startedAt }` → upsert `running`. Idempotent by `id`.
- `PATCH /api/mcp/agents/runs/{id}` `{ status, endedAt, durationMs?, inputTokens?, outputTokens?, costCents?, toolCalls?, replyMessageId?, error? }` → finish. Idempotent; a finish for an unknown id creates the row (start was lost).
- Both company-scoped, agent token must own `agentId`, payload size-capped, rate-limited per runtime.
- Server advertises capability `runs: 1` on `/runtime/register` / capabilities so bridges only report when the server supports it (**deploy order: server first, bridges second**).
- `GET /api/messages/{id}/delivery` (human session): every stored verdict for the message + linked runs + delivery_state history → the inspector.
- `GET /api/agents/{id}/runs?cursor=` (human session): recent runs, paginated.
- `GET /api/ops/storage` (platform admin): table sizes (`pg_total_relation_size`), live row estimates, last retention run.

## Bridges

- **Hermes** (`emperor_hermes_bridge.py`): generate `run_id = uuid4()` before `run_hermes`; POST start; on completion/timeout/exception PATCH finish with status, duration, the token estimate already computed for `report-usage`, tool count from the tool executor lines it already parses, reply message id. Best-effort: ledger failures never block or fail the turn; queue and retry finish once on transient errors. Report `bridgeVersion` (fix the stale `plugin.yaml` version: bump to match the server release).
- **Codex** (`emperor-codex-bridge.js` + `bridge-logic.js`): same contract.
- Both gated on the `runs` capability.

## UI

- **Delivery inspector:** a "Delivery" action on any message (chat view and Action inbox items) opening a panel: for each agent with a stored verdict → addressed or why not (`loop_paused` with streak N/12, `targeted_other`, …), the run(s) it triggered, status, duration, cost, error. Plain-language reasons.
- **Agent → Runs tab:** last runs with trigger, status, duration, tokens/cost, error; filters by status; a 30-day chart from `agent_run_daily`.
- **Ops → Storage:** table sizes, row estimates, last retention run and rows deleted.

## Risks

- **Write amplification on sync:** verdict logging runs on every sync poll → only interesting verdicts, batched, upsert; measure query time before/after.
- **Backlog delete on first deploy** → per-tick budget, batched by id.
- **Bridge/server version skew** → capability gating; bridges silently skip reporting on older servers.
- **Privacy:** no message text or reasoning in the ledger; errors redacted and truncated.
