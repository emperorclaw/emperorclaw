# Domain Flipping & Directory SEO Playbook

The actual expertise behind Domainer's mission. The agent instructions env block
covers hard operating rules (budget cap, Porkbun gating, messaging); this note
covers *how to be good at the job*, in depth.

## 1. The domain lifecycle — know the exact timeline

A domain doesn't just "expire" — it moves through a predictable ~75-day
sequence, and each stage is a different acquisition opportunity:

1. **Expiration date** — registrant didn't renew.
2. **Auto-Renew Grace Period** (~0–45 days, registrar-dependent) — domain is
   still the original owner's; they can still renew at normal price. Not
   acquirable yet, but this is when you should be *watching* a domain you
   want.
3. **Redemption Grace Period / RGP** (~30–45 days) — registry-level hold. The
   original owner can still get it back but only by paying a steep redemption
   fee (often $80–$300) directly to the registrar. Not publicly acquirable.
4. **Pending Delete** (~5 days) — locked, about to be released. This is when
   backorder services race to catch it the instant it drops.
5. **Drop** — domain becomes available to register at normal price, in a
   split-second land grab among backorder services and drop-catchers.

**Why this matters for a $100/year budget**: competing at the drop moment
against dedicated drop-catch infrastructure is not realistic for us. The
better plays are (a) backorder services where you pay only if you win, so a
missed catch costs nothing, or (b) domains that already dropped and sat
unregistered for a while (lower competition — everyone chasing fresh drops
ignores older unregistered domains that are still perfectly good), or (c)
domains still owned but abandoned (parked, dead site, no renewal urgency) —
approach the owner directly, often cheaper than any auction.

## 2. Where to actually look

- **Backorder services** (NameJet, DropCatch): pay only on a win, so queueing
  backorders on promising-but-uncertain domains costs nothing if you lose.
- **Post-drop unregistered domains**: less competitive than the drop moment
  itself. Screen expired-domain list aggregators for ones that already
  dropped and are sitting available *right now* at plain registration price.
- **Auction platforms** (GoDaddy Auctions, Sedo, Namecheap Marketplace):
  useful for research/comps even when we can't win the bidding — watching
  what similar domains sell for calibrates whether a "deal" really is one.
- **Direct outreach**: WHOIS history tools show prior registrants. A domain
  with real backlink equity but a dead/parked site, still owned by someone —
  a polite direct offer ("I'd like to buy this domain, here's what I'd pay")
  is often the cheapest acquisition path of all, no auction premium.
- **ccTLD arbitrage**: country-code TLDs (.io, .co, .to, etc.) are frequently
  undervalued relative to .com for a given keyword/niche fit — worth
  screening even if the "obvious" .com is out of budget.

## 3. Screening tools (free/low-cost — budget is $100/year, tools should be too)

- **Wayback Machine** (web.archive.org) + its CDX API — full content history,
  the single most important free tool here.
- **Common Crawl** — free, massive web crawl dataset; can approximate backlink
  presence and content history for domains not well covered by Wayback.
- **OpenPageRank** (free API, generous tier) — a rough authority proxy.
  Majestic and Ahrefs have limited free lookups too — use sparingly, don't
  need a paid subscription to screen candidates at this budget.
- **Google `site:domain.com`** — instant read on current indexation. Zero
  results after a domain clearly had content = deindex red flag.
- **Google's Search Console manual actions / transparency report** — check
  for any public penalty history tied to the domain where visible.
- **WHOIS history** (whoxy, whoisology-style lookups) — prior ownership,
  registration age, renewal pattern (a domain renewed for 15 years straight
  then suddenly dropped is a different signal than one that churned owners).

## 4. Evaluation framework — reject fast, verify hard on survivors

| Signal | What to check | Reject if |
|---|---|---|
| Backlink profile | Referring domains, anchor text distribution | Anchors are heavily exact-match/spammy, or links come from an obvious PBN network |
| Traffic history | Any available historical traffic signal | Traffic was clearly bot/spam-inflated, not organic |
| Wayback history | archive.org snapshots across the domain's life | It was ever used for spam, adult, gambling, malware, or a penalized niche (unless that IS your target niche and you understand the risk) |
| Manual actions | Google's transparency report, `site:` search | Zero indexed pages after a domain that clearly had content before (sign of a deindex penalty that may carry over) |
| Domain age & TLD | WHOIS/registration history, TLD | Very new domain (no authority to inherit), obscure/spammy-associated TLD |
| Niche fit | Does the existing authority/backlinks match a viable **directory** content shape? | Niche has no realistic "best X in Y" / comparison / listing angle |
| Trademark risk | Is the domain name a live brand? | Any real trademark conflict — not worth legal exposure at a $100 budget |
| Ownership pattern | WHOIS history churn | Domain has flipped owners rapidly and repeatedly right before drop (often a sign it's been through spam/manipulation cycles) |

**Be honest about PBNs and link schemes**: sellers will pitch domains
explicitly for "powerful backlinks" from private blog networks or clearly
manipulative link schemes. Do not buy for that reason, and do not build our
own PBN-style link schemes into any site — Google's spam policies treat both
as manipulative, and a penalty on one property can taint domains/IPs
associated with it. The legitimate play: acquire genuine residual authority,
earn rankings back with real, useful content. Slower, but the only version
that compounds instead of eventually getting deindexed.

## 5. The 301-redirect reclamation play (legitimate version)

A well-known, *legitimate* domain-flipping tactic: an expired domain with
strong topical backlinks, redirected (301, permanent) into a genuinely
relevant, better page on a site you're actively building in the *same* niche
— not a random unrelated destination, not dozens of expired domains all
funneled into one page (that pattern reads as manipulative to Google and is
explicitly against their guidelines on scaled/abusive redirects). One
topically-relevant domain, one topically-relevant destination, done sparingly,
is generally fine. Doing it at scale as a link-manipulation tactic is not —
don't.

For our directory-site model, the more durable play is usually *not*
redirecting at all: rebuild real content ON the acquired domain itself
(it already has topical authority — use it, don't discard it into a redirect)
unless there's a clear, specific reason a redirect serves users better.

## 6. Directory-SEO content strategy

What makes a directory/listing site rank and *stay* ranked, in order of
importance:

1. **Real, sourced data** — never hallucinate listings. Pull from real APIs,
   public datasets, or manual curation. A directory that's wrong erodes trust
   and gets abandoned (which Google's engagement signals will notice).
2. **Genuine uniqueness per page** — programmatic generation is fine and
   necessary at scale, but each page needs something beyond a template with
   swapped-in names: a real description, a computed score/ranking rationale,
   user-relevant filtering, something a scraped competitor page doesn't have.
   Thin, duplicate-shaped pages are exactly what Google's helpful-content
   systems suppress.
3. **Clear taxonomy / topical silos** — category → subcategory → listing,
   with real internal linking between them (breadcrumbs, related-listings,
   category hubs). This is what lets a directory rank for *category* pages,
   not just individual listing long-tails — internal links concentrate
   authority into the pages you most want to rank.
4. **Trust / E-E-A-T signals** — reviews/ratings (real, not fabricated),
   last-updated dates, sourcing transparency ("data from X, updated Y"), a
   real About page, author/editorial info if content is written not just
   listed. Google's helpful-content systems specifically look for
   experience/expertise/authority/trust signals on content that could
   otherwise look auto-generated.
5. **Structured data** — schema.org markup so listings are eligible for rich
   results (ItemList, LocalBusiness, Product/Offer, AggregateRating as fits
   the niche).
6. **Speed** — Core Web Vitals are a ranking factor and directories are
   naturally page-heavy; Astro's architecture (below) is the right tool.

**Faceted navigation trap**: filter/sort combinations on a directory can
generate near-infinite near-duplicate URLs (same listings, different sort
order). This is a classic crawl-budget and duplicate-content trap. Use
canonical tags pointing filtered views back to the clean category URL, and/or
`noindex` on filter combinations that don't deserve their own ranking, and
keep faceted URLs out of the sitemap.

**Avoid thin-affiliate patterns** Google has explicitly targeted: pure
price-comparison pages with no original content, doorway pages funneling
everything to one destination, auto-generated "best of" lists with no actual
evaluation behind them.

## 7. Monetization (so the site is worth building, not just ranking)

Pick a model that fits the niche before building, since it shapes the content
structure:
- **Affiliate** — comparison/review directories linking to vendor signup —
  requires clear FTC-style affiliate disclosure on every monetized page.
- **Featured/paid listings** — businesses pay for placement — needs enough
  directory traffic first to have leverage to sell.
- **Lead-gen** — capture user inquiries, sell/route them to listed
  businesses — common for local-service directories.
- **Display ads** — simplest, lowest revenue per visitor, needs real scale
  to matter.
Whatever the model, don't let it distort the core rule from section 6: the
content has to be genuinely useful first, monetization second — a directory
optimized purely for ad/affiliate revenue with thin listings is exactly the
helpful-content-update target.

## 8. Astro implementation — concrete patterns

Astro is the right stack because directory sites are "many mostly-static
pages generated from structured data" — exactly Astro's strength (zero
client JS by default, static output, content-collection-driven generation).

**Data layer** — Content Collections with a typed schema:
```ts
// src/content/config.ts
import { defineCollection, z } from 'astro:content';

const listings = defineCollection({
  type: 'data', // JSON/YAML entries
  schema: z.object({
    name: z.string(),
    category: z.string(),
    slug: z.string(),
    description: z.string(),
    rating: z.number().min(0).max(5).optional(),
    website: z.string().url().optional(),
    lastVerified: z.coerce.date(),
  }),
});

export const collections = { listings };
```
For very large or frequently-refreshed datasets, Astro's newer Content Layer
API can pull directly from a remote API/database at build time instead of
committed JSON files — worth using once a directory outgrows hand-managed
data files.

**Page generation** — `getStaticPaths()` generates one static HTML page per
listing and per category at build time (`output: 'static'`, Astro's
default): fully crawlable, fast, and serves from any static host/CDN with no
server compute cost.
```ts
// src/pages/listings/[slug].astro
export async function getStaticPaths() {
  const entries = await getCollection('listings');
  return entries.map((entry) => ({
    params: { slug: entry.data.slug },
    props: { entry },
  }));
}
```

**Islands architecture** — keep the page itself zero-JS. Hydrate only the
specific interactive bits (search box, filter widget, sort control) as
isolated islands (`client:load` / `client:visible` on a small
React/Vue/Svelte/Preact component) — don't ship a JS framework for the whole
page because one widget needs interactivity. Client-side filtering should
never be the *only* way to reach content — category pages need to exist as
real crawlable URLs too, not just a filtered view of one big page.

**SEO plumbing**:
- `@astrojs/sitemap` for an auto-generated sitemap (exclude faceted/filtered
  URLs — see section 6).
- A shared `Layout.astro` enforcing canonical URLs, meta description, Open
  Graph tags, and JSON-LD structured data per page type.
- `astro:assets` for optimized images (responsive sizes, modern formats)
  instead of hand-managed `<img>` — matters directly for LCP.
- Font loading: self-host or `font-display: swap` — avoid render-blocking
  web fonts, another common Core Web Vitals hit on content-heavy sites.

**Build pipeline for scale**: a small generator script takes the raw data
source (CSV/JSON export, or an API pull) and emits/updates content collection
entries, so refreshing listing data is a repeatable script run, not manual
editing. This is what makes 1,000+ listings tractable.

**Deployment**: static output works on any static host (Cloudflare Pages,
Netlify, Vercel, GitHub Pages). No target has been chosen yet — ask before
deploying anywhere; don't assume.

## 9. Compliance checklist before launch

- Affiliate links: clear disclosure per applicable regional rules (FTC-style
  in the US, similar elsewhere) on every page with monetized links.
- Scraped/aggregated data: confirm the data source's license/terms actually
  permit redistribution in a directory — "I found it on the web" is not a
  license.
- User-submitted content (reviews etc.): basic privacy handling if you store
  any personal data — don't collect more than the feature needs.
- Post-purchase: enable WHOIS privacy on the new registration immediately —
  don't leave the operator's personal info exposed in public WHOIS.
